## Причина инцидента

В DE browser container подтверждены `oom_kill=1` и Docker `OOMKilled=true` при
лимите 1 GiB. Контейнер оставался запущенным и healthy: прежняя проверка отвечала
только за HTTP RPC. Coordinator постоянно возвращался в pending после неудачного
открытия, revision росла, новых photo outbox записей не появлялось. Последние
картинки относились к предыдущей успешно пройденной CAPTCHA. Поиск оставался
включённым, но получал `JOB_HH_MANUAL_ACTIVE`; 46 поисковых окон были сохранены.
Точный exception открытия старый обработчик потерял, конкретный убитый subprocess
поэтому не установлен. Независимый Chromium с отдельным профилем смог открыть HH.

## Исправление

Подготовка закрывает старую вкладку и создаёт новую, учитывает событие crash.
Health проверяет локальное выполнение JavaScript в Chromium, watchdog и предел
операции не дают HTTP-сервису скрывать потерю или зависание браузера. Основной
процесс завершится с ошибкой, чтобы штатная Docker policy восстановила его с
прежними profile/journal/claims. Обычное завершение не вызывает fatal recovery.

Запрос обновления сохраняется до durable результата и подтверждается по своему
UUID: новый клик нельзя удалить подтверждением старого. Ошибки подготовки дают
растущую паузу до двух минут и фиксированное уведомление. Telegram 429 допускает
не больше четырёх попыток одной photo-записи; потеря ACK или lease становится
unknown. Неизвестный результат ответа HH также блокирует автоматическую замену.
Явное обновление запрашивает новую картинку, не повторяет старый answer POST.

Просроченная/использованная/потерянная картинка требует обновления с понятным
сообщением. При idle явный запрос сообщает об отсутствии активной CAPTCHA,
не объявляя доступ к HH проверенным. Новые уведомления используют прежний outbox,
проверяют owner/Telegram identity/conversation/chat и дедуплицируются. Неактуальные
queued сообщения о задержке снимаются после подготовки результата.

Migration 033 только добавляет метаданные. Лимит памяти, профиль, фильтры,
прогресс, пауза и границы однократной отправки сохранены. Новых зависимостей нет.

## Проверки

- Server: 643/643; обязательный Telegram gate: 65/65.
- Linux browser unit/HTTP: 45/45, без пропусков.
- Настоящий отдельный PostgreSQL: 9/9, включая реальные message/menu handlers
  и повтор уведомления после временного сбоя проверки scope до отправки.
- Chromium HTTPS: 5/5, включая намеренное падение renderer, неизвестный ответ,
  restart, native POST и точную проверку исходного target.
- Три отдельные runtime проверки: прежняя pending pause и потеря context;
  первая human CAPTCHA без OCR; фактическое завершение main после убийства своего
  Chromium и запуск с прежними claims. Все прошли.
- Compose CAPTCHA policy: 4/4. `git diff --check` без ошибок.

Первые запуски стенда выявили неготовность нового тестового PG и дублирующий
conversation ключ в новой фикстуре; readiness проверен, фикстура исправлена.
Итоговые проверки выше прошли на изолированных данных, без обращений к Telegram
и без отправки ответа настоящему HH. Одноразовые HTTPS fixtures не имели внешней сети.

## Что осталось для выпуска

Нужно отдельное поручение на публикацию: GitHub main и оба VPS source;
на DE — server с migration 033 и browser с согласованным private protocol.
Collector runtime не меняется. Затем проверить health, настоящую доставку фото,
ответ владельца и продолжение сохранённого поиска. Desktop не изменён.
До этого текущий production-инцидент не считается устранённым.
