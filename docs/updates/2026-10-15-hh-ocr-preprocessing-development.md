# Исправление подготовки изображений OCR HH: локальные результаты

15 октября 2026. Выполнен согласованный offline этап по
[исследованию](2026-10-15-hh-ocr-research.md) и
[плану](../superpowers/plans/2026-10-15-hh-ocr-preprocessing.md).
Новые исходники и тестовый образ подготовлены, в GitHub и production не установлены.

## Причина и изменения

Прежний алгоритм перебирал 25 вариантов только верхней дуги. Новый образец
имел нижнюю U-образную дугу; этот тип ранее не обрабатывался. Опыт с обеими
ориентациями устранил пустой результат на одном из ранее отклонённых образцов.
Простой перевод в чёрно-белый формат, изменение цветовых каналов, масштаба,
локального контраста и удаления фона сами по себе устойчивого допуска не дали.

Теперь небольшой `job-ocr/preprocessing.py` формирует четыре варианта без
выпрямления и по 25 вариантов верхней/нижней дуги. Пороги сохранены: confidence
не ниже 0.85, минимум четыре совпадения, не менее 60% допустимых кандидатов.
Число вариантов не означает независимые подтверждения правильности строки.
Для нового пути без выпрямления tensor ограничен высотой 48 и шириной 16–1024;
широкий тонкий PNG не вызывает неограниченного выделения памяти.

Отказ без согласованного текста теперь даёт закрытые `OCR_NO_CONSENSUS` в HTTP
и `JOB_OCR_NO_CONSENSUS` в worker logs. Ошибки входа и результата отличаются
собственными закрытыми кодами. Произвольные сообщения исключений не выводятся.
Успешный ответ остаётся строго `{answer: string}`. Browser RPC, Telegram,
owner binding, модель, веса, зависимости и запрет повтора неизвестного POST не менялись.

## Сравнение в готовом образе

| Вход | Прежний алгоритм | Новый алгоритм |
| --- | --- | --- |
| Старый читаемый screenshot | Допуск | Допуск: 19 из 25 допустимых кандидатов согласны |
| Сохранённый проблемный screenshot | Пустые строки, отказ | Допуск: 10 из 16 допустимых кандидатов согласны |
| Оригинальный PNG другого нового задания | Отказ | Отказ: 13 из 24, меньше 60% |
| Screenshot того же нового задания | Отказ | Отказ: 13 из 23, меньше 60% |
| Белое изображение, случайный шум, PNG 2048×1 | Не являются контрольными заданиями HH | Отказ без согласованного результата |

Это три разных настоящих изображения капчи; original/screenshot последнего
не считаются независимыми заданиями. Результат «допуск» означает выполнение
правила OCR, а не принятие ответа HH. Новые строки не имеют независимо
подтверждённой разметки; точность в процентах по этим опытам не заявляется.

Оригинальный PNG последнего задания 250×90, RGBA, один кадр. Screenshot 402×117
меняет пропорции, однако оба варианта остаются неоднозначны. Перенос browser
на оригинальные PNG пока не выбран: устойчивого выигрыша не подтверждено.

## Проверки и ресурсы

- Пять Python unit tests прошли в готовом образе: формат ответа, согласие,
  входные ограничения, ограничение tensor и закрытые diagnostics.
- Семь model acceptance случаев выше прошли в отдельном контейнере: network
  none, read-only rootfs, cap_drop ALL, CPU 1, память 512 MiB, pids 64.
  Обработка 1.0–1.4 секунды на вход, peak RSS процесса около 118 MiB.
- Три настоящих UNIX HTTP случая прошли с новым worker и прежним Node client:
  проблемный screenshot — HTTP 200 и ответ только с `answer`; неоднозначный —
  HTTP 422 / `OCR_NO_CONSENSUS`; неверный PNG — HTTP 422 / `OCR_INPUT_REJECTED`.
  Socket volume со стороны client read-only. Тестовый worker и volume удалены.
- Собран `jarvis-job-ocr-preprocessing-candidate:20261015`. Модель и пакеты
  прежние pinned; новых production-зависимостей нет. Код production не подменялся.

Изображения и строки опытов остаются в приватных временных артефактах, не в Git.
Для сравнения original/screenshot один раз получена новая картинка через узкую
инициализацию; ни одного POST ответа или отклика не было. Штатный browser
восстановлен, owner-bound journal не менялся, progress поиска сохранён.

## Следующий выпуск

Нужны поручение на публикацию и живое подтверждение. По release-workflow:
опубликовать GitHub main, синхронизировать оба VPS, на DE пересобрать только
job-ocr и проверить его health. Server/browser/collector не изменились,
Desktop и VPN обновлять не требуется. Последующие MD-only коммиты не требуют
перезапуска компонентов. Не сбрасывать incident и не повторять неизвестный
POST автоматически; возможная новая попытка должна учитывать исходный журнал.

Неоднозначные изображения всё ещё могут требовать ручной проверки. Этот ремонт
устраняет конкретный пробел геометрии и добавляет диагностику, но не гарантирует
прохождение каждой капчи HH.
