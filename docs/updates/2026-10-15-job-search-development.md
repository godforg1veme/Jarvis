## Реализовано локально

Отдельная конфигурация, широкий детерминированный отбор, консервативные правила
оплаты, PostgreSQL-репозитории, устойчивые прогресс сбора и очередь карточек.

3 USD является уведомлением. Настройки, профиль и правки используют typed
guided input и проверку владельца. Встроен opt-in runtime и отдельный entrypoint
сборщика без Telegram polling. Feature по умолчанию выключена.

## Расхождение HH API

Во время реализации загружена текущая официальная
[OpenAPI-спецификация](https://api.hh.ru/openapi/specification/public),
на которую ссылается [официальный репозиторий](https://github.com/hhru/api).
В ней нет прежнего метода `POST /negotiations` соискателя и `/resumes/mine`.
OAuth и операции работодателя в документе остаются; наличие OAuth не
доказывает право отправлять отклики соискателя. Старые страницы Markdown
ссылаются на отсутствующие операции, поэтому прежнее утверждение об отправке
через API не является достаточным подтверждением.

Владельцу сообщено об ограничении; выбор между выяснением доступа,
временной ручной отправкой и обсуждением браузерного канала запрошен отдельно.
Ни один из вариантов не считается молчаливо одобренным. Исходная цель остаётся
активной, успех тестового HTTP-стенда не заменяет подтверждение реального API.
Позднее владелец подтвердил наличие зарегистрированного HH-приложения.
Это обновляет сведения о регистрации, но доступ соискателя пока не проверен.
Настройки HH не обнаружены в работающем DE-контейнере и локальном `.env`
под поддерживаемыми именами; запрошено их расположение без значений секретов.

## A2A

[A2A](https://a2a-protocol.org/latest/) описывает обмен независимых агентных
систем. В согласованной функции такого соединения нет, поэтому добавление
протокола ради теста не требуется. Проверяются реальные границы функции:
Telegram, HH, модель, PostgreSQL и самостоятельный сборщик. Это не называется
проверкой соответствия A2A.

## Browser reader, RPC и сборщик — последующая контрольная точка

Добавлены отдельный браузерный runtime и закрытый RPC с одним owner UUID,
constant-time проверкой секрета, строгими аргументами и ограничениями размера.
Сборщик использует этот клиент вместо HH API. Browser не подключён к PG-сети,
не получает DB/model/Telegram env и не публикует host ports/CDP. Приватный
volume остаётся отдельным, owner binding не допускает смену UUID.

Нормализация читает JobPosting и видимые поля зарплаты, налогов, периода,
формата работы и занятости. Неизвестное сохраняется явно. HH подтвердил
отдельный empty-search block; он отличается от изменённого или незагруженного
DOM. Page count и 20 карточек сверяются; сборщик не делит browser-периоды
через игнорируемые параметры API. При ошибке checkpoint не продвигается.

На живом HH DE адаптер прочитал первую страницу, полную вакансию и два резюме.
Основное резюме найдено. Read-only inspect формы вернул `resumeAvailable=true`,
`manualRequired=true`, `JOB_HH_RESUME_HIDDEN`. Дополнительно в собственных
прошлых откликах наблюдены селекторы уже отправленного отклика; они блокируют
новую автоматическую отправку, но сами по себе не доказывают ID результата.

Проверки: 12/12 browser unit, 626/626 server unit, 13/13 PG acceptance,
1/1 Telegram/HTTP E2E и 1/1 full runtime с 32 миграциями. Два отдельных
Chromium acceptance покрывают чтение/форму/блокировку write и запуск runtime,
auth health, чужой owner и сохранённую привязку профиля. Fixtures работают

## Исправление проверки видимости и сохранение стоп-листа

Владелец уточнил, что резюме должно оставаться скрытым от уже выбранных
работодателей и доступным остальным. Read-only проверка карточки резюме
подтвердила именно этот режим. Предыдущий вывод о необходимости открыть
резюме всем был ошибочным: скрытый zero-size блок `hidden-resume-warning`
имел client rect, поэтому проверка считала его видимым. В трёх разных формах
Playwright подтвердил, что предупреждение скрыто, а кнопка не заблокирована.
`isVisible()` исправляет этот случай; явное видимое предупреждение продолжает
останавливать подготовку. Изначальный запрос на изменение видимости отменён
этим уточнением; вмешательство владельца для смены настроек не требуется.

Добавлено чтение выбранного режима и существующего списка через UI без
изменения radio, удаления компаний или сохранения формы. Проверяются пустой
поиск, строки/ссылки работодателей, кнопки удаления как признак состава списка,
отсутствие неизвестных действий и стабильность списка после прокрутки.
Неполная или изменившаяся структура не разрешает считать компанию отсутствующей.
ID работодателя читается из карточки вакансии. При совпадении inspect блокируется;
неизвестный ID/список также блокирует подготовку. Список не передаётся модели.

На DE прочитан текущий список из десяти компаний; новый reader вернул
`mode=blacklist`, `complete=true`. Для обычной вакансии последующий inspect
вернул `resumeAvailable=true`, `manualRequired=false`. Это чтение существующих
данных; настройки HH, резюме и отклики не менялись. В
[официальной справке HH](https://feedback.hh.ru/knowledge-base/article/1897)
указано, что отклик компании из стоп-листа автоматически удаляет её из него;
поэтому одного сохранения radio-настройки недостаточно — нужен запрет отклика.

Также добавлены Linux durable ledger, проверка точного письма и координатор
отправки с инъекцией typed driver. Журнал хранит хеш письма, owner/operation
и хеш пары; fsync и атомарная публикация исключают повторный клик после
неизвестного результата и смены ID. Подтверждённый результат неизменяем.
Повреждённый файл, чужой scope, symlink или доступные другим пользователям
права блокируют действие. Подготовка поля блокирует unsolicited autosave.
Chromium fixture с тестовым endpoint проверяет единственный POST, lost ack,
перезапуск и сверку без повторной отправки. В production RPC submit/reconcile
по-прежнему недоступны: реальный driver и доказательство результата HH остаются.

Итог этой контрольной точки: 15/15 browser unit выполнены на DE Linux без сети
и без пропусков. Дополнительно прошли два Chromium fixture acceptance —
read/inspect с сохранением стоп-листа и preparation/submission coordinator с
тестовым endpoint. Две Linux ledger-проверки входят в unit-набор; их отдельный
запуск также прошёл. Проверка runtime из прошлого этапа не повторялась:
startup/Compose в этой правке не менялись. Это не production-выпуск.

## Драйвер отправки и подключение к серверу — следующая контрольная точка

Наблюдаемый публичный код формы HH подтвердил: UI отправляет FormData через
`/applicant/vacancy_response/popup`. Драйвер нажимает штатную кнопку; page guard
разрешает ровно один POST только после durable claim. Проверяются точные
vacancy/resume/letter и поля формы. Изменение видимости по странам, дополнительные
вопросы, файлы, неизвестные поля и повторный запрос блокируются. Прямой HTTP
обход формы не используется. Ответ подтверждается native topic/chat и связью
статуса с выбранным резюме и вакансией; неполный ответ остаётся unknown.

Read-only восстановление читает штатную ссылку существующего отклика и его
чат: требуется собственный application bubble с точным письмом, а также
совпадение вакансии, native resume/topic/chat. На настоящем прошлом отклике
HH проверены положительный результат и отказ для изменённого текста.
Текст старого письма сравнивался в памяти; в отчёт и Git не сохранялся.
Новых откликов или сообщений эта проверка не отправляла.

Submit/reconcile теперь подключены к RPC и opt-in runtime. Отдельный apply
credential обязателен и отличается от read credential. Сборщик его не получает.
BrowserMain сериализует чтение и отправку одним профилем; журнал переживает
рестарт. Сервер передаёт в reconcile исходный одобренный текст из PostgreSQL.
«Подключить HH» проверяет уже выполненный вход/основное резюме и синхронизирует
локальные метаданные; повторный connect не повышает revision, замена резюме
отклоняется. Cookies остаются только в приватном browser volume.
