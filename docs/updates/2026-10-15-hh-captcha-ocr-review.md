# Проверка ddddocr перед экспериментом с капчей HH

15 октября 2026. Это результат проверки стороннего пакета и условия будущего
эксперимента. OCR не установлен в Jarvis, автоматическое прохождение капчи
не подключено. Проверка не является гарантией отсутствия вредоносного кода.

Более поздний результат того же дня: ddddocr исключён из реализации из-за
неподходящего алфавита. Для реальной русскоязычной картинки выбран официальный
PaddleOCR ONNX; отдельно проверены модель, pinned runtime и изоляция. Подробности
и фактические тесты — в [записи разработки](2026-10-15-hh-captcha-recovery-development.md).

## Что проверено

- Официальный пакет PyPI: `ddddocr==1.6.1`, а не отдельный пакет
  с похожим именем `ddddocr-1.6.1`.
- Wheel: `ddddocr-1.6.1-py3-none-any.whl`, 75 983 593 байта.
  SHA-256 совпал с метаданными PyPI:
  `c7c70f4ae2d0335440ae8b272eea48c9f6888ecef46785fe2311f0c97a133935`.
- Все 28 Python-файлов wheel совпали с исходниками GitHub
  `sml2h3/ddddocr`, commit `c40f56f95412e10bcb9bd0bd24411e92f896d238`.
  Проверены импорты и вызовы через AST, загрузка моделей, обработка изображений,
  точки входа и встроенные HTTP/MCP-модули. Wheel не содержит `.pth`.
- Не обнаружены вызовы shell, `eval`, `exec`, pickle или сетевых клиентов
  в Python-коде wheel. Рекламные URL в конструкторе печатаются, обращения
  по ним не выполняются. Для эксперимента нужен `show_ad=False`.
- Три встроенные ONNX-модели побайтно соответствуют GitHub blobs.
  В просмотренных верхнеуровневых графах нет ссылок на внешние tensor-файлы.
  У `common_old.onnx` есть домен `com.microsoft` и операция
  `DynamicQuantizeLSTM`; это само по себе не признак вредоносного кода.
  Структурный просмотр не проверяет все вложенные графы и не доказывает
  отсутствие ошибок в нативном runtime или нежелательного поведения модели.
- Windows Defender: выполнен CustomScan каталога с wheel и исходниками,
  соответствующих обнаружений нет. Защита включена, дата сигнатур — 14 октября.
- OSV querybatch: нет известных advisories для `ddddocr 1.6.1` и проверенных
  кандидатов: numpy 2.5.4, onnxruntime 1.31.0, pillow 12.3.0,
  opencv-python-headless 5.0.0.93, flatbuffers 25.12.19, packaging 26.3,
  protobuf 7.36.2, sympy 1.14.0, mpmath 1.4.1, coloredlogs 15.0.1,
  humanfriendly 10.0. Эти версии не являются согласованным lock-файлом:
  например, numpy 2.5.4 требует Python 3.12+, а mpmath 1.4.1 не проходит
  ограничение sympy 1.14.0. Перед запуском нужно разрешить фактическое дерево
  зависимостей под выбранный Linux/Python, закрепить wheel hashes и повторить
  проверку именно полученного набора. Нативные wheel зависимостей здесь
  не скачивались и на вредоносный код не проверялись.

Пакет и его установочные команды не выполнялись. Артефакты проверки находятся
во временном каталоге вне репозитория; секреты и профиль HH в него не передавались.

## Выявленные ограничения

1. Встроенный HTTP/MCP-сервер позволяет менять конфигурацию моделей и не должен
   становиться публичным сервисом Jarvis. Есть permissive CORS и возможность
   передавать путь к модели. Для эксперимента эти модули не нужны.
2. OCR API допускает строковые локальные пути. Не передавать ему непроверенную
   строку, URL, путь пользователя или данные страницы как путь к файлу.
3. Экспорт констант размера изображения не гарантирует их применение на всех
   путях обработки. Проверять размер до буферизации/декодирования, затем формат,
   размеры и число пикселей; декодировать в ограниченном процессе.
4. Production dependencies в upstream не закреплены. Обычный `pip install`
   без lock/hashes не воспроизводит эту проверку.
5. ONNX Runtime, Pillow и OpenCV содержат нативный код. Совпадение с upstream,
   антивирус и отсутствие известных advisories не исключают неизвестных ошибок.

## Граница против prompt injection

Картинка капчи и результат OCR являются недоверенными данными. OCR не должен
вызывать LLM, Tool Gateway, shell, читать память или принимать решения Jarvis.
Ответ используется только как значение поля заранее проверенной формы капчи.

Перед отправкой нужен закрытый формат результата: строка с ограниченной длиной
и разрешённым алфавитом, выбранным после просмотра реальной картинки и формы HH.
Инструкции, URL, JSON, переносы строк и лишние поля отклоняются. Даже строка,
прошедшая алфавитную проверку, остаётся только ответом капчи и не приобретает
полномочий команды. Текст распознавания не попадает в промпты, память или логи.

Работник получает только ограниченное изображение, без cookies, профиля HH,
Telegram/OpenRouter/API credentials, PostgreSQL и Docker socket. Сеть отключена,
порты не публикуются, непривилегированный пользователь, read-only rootfs,
отдельный временный каталог и лимиты времени, CPU, памяти и процессов.
Модели выбираются из закреплённого набора, произвольные пути запрещены.

Успешное распознавание ещё не означает успешное прохождение: браузер должен
проверить результат HH. Разрешение на отправку ответа капчи не разрешает
отклики, изменение резюме или ослабление общей защиты POST-запросов.

## Следующий этап

эксперимент распознавания обрезанного изображения. Само прохождение капчи,
повтор через две минуты и интеграция в collector пока не реализованы.

публикация GitHub/VPS следует обычному release-workflow.
