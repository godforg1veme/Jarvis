# Приоритет обработки вакансий в браузере HH

Продолжение порученного ускорения серверного HH: закрыть пункт 4 полностью,
сохранив принятые 3 CPU и кэш резюме. Результат включает работающий browser и замеры.

## Решение

Каждый HH-профиль сохраняет одну активную операцию. История становится фоновой
очередью, остальные операции сохраняют обычную очередь. При выборе следующей
операции обычная очередь проходит раньше истории; после четырёх обычных операций
при ожидающей истории выполняется её старейшая задача. Внутри очередей FIFO.
Начатая операция не прерывается. Внешний RPC не получает параметра приоритета.
`tail` продолжает означать завершение всей очереди для смены резюме и shutdown.

## Проверки и замеры

- [x] Проверить чистоту main, ветки, worktrees и PR перед изменением.
- [x] Реализовать очередь и проверить последовательность, fairness, reject,
  timeout, независимость профилей, вызов history и полное ожидание `tail`.
- [ ] Сравнить штатный read-only RPC: активное чтение резюме, ожидающая история,
  затем чтение вакансии. Записывать только длительности и коды, без содержания.
- [x] Из сохранённых owner-scoped контрольных точек измерить полный цикл
  после кэша: оценку/отсев и попытку с письмом до фактического конечного состояния.
  Отдельно обозначить manual/unknown; не выдавать их за успешный отклик.
- [ ] Пройти тесты browser/server, собрать immutable browser image, сохранить
  HH profile volume и окружение, заменить только browser, проверить health и 3 CPU.
- [ ] Повторить read-only сравнение на установленном образе; подтвердить,
  что история тоже завершается. Измерить последующие реальные автоматические циклы.
- [ ] Обновить RU/EN текущий статус и запись о выпуске, синхронизировать оба VPS.

Формы и классификация ошибок остаются пунктами 2 и 5 исходного списка.
Задача скорости не изменяет разрешения на отправку или неизвестные операции.
