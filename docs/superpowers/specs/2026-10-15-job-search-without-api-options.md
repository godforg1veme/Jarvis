# Поиск работы без API соискателя HH

15 октября 2026. Владелец согласовал браузер на DE и Playwright/Chromium.
Следующий этап — проверочный прототип без отправки реальных откликов.
Владелец привёл уведомление HH: поддержка API для соискателей прекращена
15 декабря 2025 года, и поручил найти другой способ. Регистрация приложения
и его ключи больше не рассматриваются как решение подключения соискателя.

Ранее согласованные пользовательские требования находятся в
[основной спецификации](2026-10-15-job-search-design.md). Её предположение
об официальном applicant API отменено новым поручением. Требования к фильтрам,
Telegram, фактам, письмам, подтверждениям, бюджету и отдельному процессу DE
сохраняются. Выбран браузерный канал; дополнительно поручено исследовать
фактически встречающиеся проверки безопасности HH в процессе работы.

## Варианты

| Вариант | Что даёт | Ограничения |
| --- | --- | --- |
| Браузерный процесс на DE | Собственный обход страниц поиска по расписанию, чтение полных вакансий, заполнение формы отклика после подтверждения | Нужно проверить доступ HH с DE, вход, элементы страниц, восстановление сессии и доказательство результата; нужен отдельный browser runtime |
| Почтовый автопоиск HH + браузер для откликов | Новые ссылки поступают через поддерживаемые уведомления; почтовый адаптер затем пригодится LinkedIn | Расписание доставки определяет HH; собственные 30 минут и полнота истории за 14 дней не обеспечены одной рассылкой; полные тексты могут потребовать браузера |
| Браузер на Windows | Вход и работа с HH рядом с пользователем; возможный запасной вариант при проблемах DE | Отправка зависит от включённого компьютера, требуется отдельное согласование изменений Desktop |

Рекомендация: сначала проверить браузерный процесс на DE. Он ближе всего
к принятому требованию автономности. Почтовые уведомления — возможный второй
входной канал, а не молчаливое изменение частоты или полноты поиска.

## Предлагаемый путь

1. Отдельный процесс с Playwright и Chromium читает страницы поиска HH
   каждые 30 минут и передаёт нормализованные вакансии существующему домену.
   Первый проход запрашивает последние 14 дней; полнота и пагинация проверяются
   по фактическому поведению сайта. Модель в сборе не участвует.
2. Владелец входит в отдельный браузер HH через защищённый доступ. Наличие
   сессии и возможность длительной работы проверяются практически. Вход
   нельзя обещать как одноразовый навсегда: HH может потребовать повторную
   авторизацию. Коды и пароль вводятся в браузере, не в Telegram или чате разработки.
3. После выбора карточки сохраняется согласованный сценарий: письмо,
   правки/перевод, просмотр, отдельное подтверждение точных вакансии,
   основного резюме и версии текста. Только затем браузер отправляет форму.
4. Адаптер реализует ограниченные inspect/submit/reconcile. Модель не получает
   произвольное управление браузером или shell. Внутренние недокументированные
   HTTP-методы HH не являются основой предлагаемого варианта.
5. Операция записывается до нажатия отправки. Потеря ответа оставляет unknown;
   повторный клик не выполняется. Браузер проверяет исходный результат в HH.
   Как доказать принадлежность найденного отклика исходной операции, нужно
   установить на реальном интерфейсе, а не предположить по локальному стенду.
6. Истёкшая сессия или CAPTCHA переводят работу в ожидание действий владельца.
   Анкеты и дополнительные вопросы не заполняются выдуманными ответами.
   После восстановления проверяется исходная операция и её актуальность.

Профиль браузера — секрет: приватное хранилище вне Git, без cookies, заголовков,
тел страниц и снимков личного кабинета в логах. Browser/CDP-порты не публикуются
в интернет. Сборщик и браузер получают только необходимые права; PostgreSQL
остаётся приватным, Docker socket и sudo не требуются.

## Первый проверяемый этап

Проверить на DE открытие поиска, одну полную вакансию, вход владельца, список
собственных резюме и подготовку формы без финального нажатия отправки.
Одновременно проверить реальную возможность увидеть существующий отклик.
Зафиксировать селекторы, ограничения и потребление ресурсов; прежний лимит
памяти простого HTTP-сборщика нельзя автоматически переносить на Chromium.
Если этот этап не проходит, пересмотреть вариант до переписывания адаптеров.

Затем составить обновлённый план и реальные browser-fixture/E2E проверки:
изменение страницы, отсутствие элемента, timeout до/после клика, повторное
подтверждение, истечение сессии, чужой scope и смена резюме. Предыдущие
PostgreSQL/Telegram тесты сохраняются, но не считаются доказательством
работы сайта. Реальный отклик требует выбора вакансии и подтверждения владельца.

Playwright и Chromium являются новой production-зависимостью этого варианта;
по AGENTS.md их добавление требует согласования, полученного в текущем чате.
Исследование проверок не означает заранее согласованный механизм их обхода.
Push и выпуск требуют отдельного
поручения по действующему release-workflow.

## Основания и границы уверенности

- [HH: автопоиск вакансий](https://hh.ru/article/14) описывает сохранённые
  запросы и ссылки в почтовых уведомлениях; не доказывает требуемую полноту
  и частоту доставки для Jarvis.
- [Playwright: авторизация](https://playwright.dev/docs/auth) описывает
  повторное использование состояния браузера и его чувствительность.
  Это возможность инструмента, а не доказательство совместимости с HH.
- Дата прекращения API получена из уведомления, приведённого владельцем.
  Текущий прототип не проходил авторизованный browser E2E HH на DE.
