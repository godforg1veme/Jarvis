# HH: состояния и безопасное восстановление

## Согласованный результат

Владелец поручил последовательно реализовать общий ремонт автооткликов:
подтверждение HH, состояния до/после отправки, читающую сверку, контракт письма,
правдивые уведомления и сквозные проверки. Работа локальная; публикация и
новые реальные отправки этим этапом не поручены.

## Подтверждённый источник

На отдельной временной копии собственной сессии при запрете всех изменяющих
запросов найден GET `https://chatik.hh.ru/chatik/api/chat_data?chatId=...`.
Ответ содержит chat/resources/messages и точный текст исходного письма.
WebSocket остаются запрещены. Читатель ограничивает размер до JSON-буферизации
и возвращает только результат проверки, не сообщения, профили или токены.
Доказательство связывает vacancy/resume/topic/chat, текущего участника и
единственное сообщение отклика с точным исходным письмом. При недостаточном
доказательстве результат остаётся unknown. Для анкет требуется доказательство
точных ответов; обычное письмо не заменяет его.

## Состояния и восстановление

- До durable claim нельзя сообщать о неизвестной отправке: подтверждённый
  отказ подготовки получает отдельный безопасный код без повторного POST.
- После claim/возможного dispatch неизвестный исход остаётся unknown с исходным
  ID. Сверка ограничена числом попыток и паузами, выполняет только чтение,
  проверяет текущие права и исходный личный scope. Никогда не вызывает submit.
- Ошибка структуры/фактов полученного письма является известным отказом до HH.
  Контракт провайдера и парсера согласованы. Допускается одна дополнительная
  генерация в той же логической задаче, с сохранённым checkpoint до вызова и
  отдельным детерминированным usage ID. Прерванный/неизвестный вызов не повторяется.
- Два невалидных ответа передаются пользователю как ошибка письма, без HH
  operation. Неизвестный ответ модели отличается от неизвестной отправки HH.
- Выключение, отзыв доступа и смена подключения не запускают новых действий.
  Читающая сверка не включает автоматику и не изменяет личные настройки.
- Старые записи без доказательства стадии не переименовываются в успешные или
  точно неотправленные. Старые неизвестные вызовы не повторяются под новым ID.

## Контракты и границы

CommonJS, текущая модель и ограничения цены, без новых production-зависимостей.
Код общий для owner/member; каждый профиль, резюме, письмо и анкета изолированы.
Сохраняются callbacks, guided-input kinds, подтверждения и личные разрешения.
Уведомления сообщают стадию и фактическое следующее действие. Диагностика —
закрытые phase/code/attempt, без текста, ответов, cookie и сырых исключений.
Изменения БД forward-only и с настоящими PG acceptance.

## Приёмка

Проверить GET-доказательство с неверными owner/resume/vacancy/topic/letter,
malformed/oversized ответом, отсутствующим письмом, blocked WS и запретом POST.
Проверить lost receipt → чтение исходного ID → sent без второго submit;
ошибку до reserve; invalid letter → одна repair → draft либо конкретный отказ;
неизвестную модель без повторов; off/revocation; рестарт; owner/member и анкету.
Фикстуры не считаются доказательством новой живой отправки. Для принятия
потребуется отдельно согласованный выпуск и проверка реального нового отклика.
