# Telegram Mini App Jarvis

Статус: визуальное направление и модель прав согласованы в чате 18 октября
2026; письменная спецификация подготовлена для проверки владельцем.
Это планируемая функция, а не описание установленной версии.

## Решения владельца

- Telegram Mini App является полноценным клиентом существующего Jarvis.
- Главный администратор — текущий владелец; только он назначает и снимает
  полных администраторов. Нельзя заблокировать, понизить или заменить владельца
  через обычный API администрирования.
- Другие администраторы управляют системой, обычными ролями и доступами.
  Это не даёт чтения чужих диалогов, памяти, документов или подключений.
- Одна обычная роль на пользователя; у роли галочки по разделам.
- Дополнительно у каждого пользователя для каждого раздела есть три состояния:
  `inherit`, `allow`, `deny`. Явная личная настройка имеет приоритет над ролью.
- Email отсутствует в модели, приглашениях, формах и списках. Идентичность
  определяется числовым Telegram ID, хранимым как строка. Имя и необязательный
  username являются только отображаемыми атрибутами, а не доказательством прав.
- Новая production-зависимость Three.js явно согласована владельцем в чате.

## Интерфейс

Визуальное направление: графитовый фон, светлый текст, холодный голубой акцент,
металлические кольца вокруг светящегося ядра. Эталон — показанный в чате
макет 18 октября; он не является готовой 3D-моделью.

Нижняя навигация: Главная, Ассистент, Управление. Последний пункт доступен
только главному администратору и администраторам. Главная показывает только
разрешённые разделы. Главное и помощь доступны всем активным участникам.
Обычный диалог с ассистентом — отдельное разрешение.

Разделы: assistant, jobs, life, memory, documents, devices, vpn, operations.
Одна галочка означает доступ ко всем уже предусмотренным действиям раздела
в пределах собственных ресурсов и существующих подтверждений. Она не открывает
чужие ресурсы и не обходит закрытые playbooks Supervisor или локальные Vision
leases. Новые разделы выключены у обычных ролей по умолчанию.

Управление: список людей с Telegram ID, поиск по ID/имени, роли, создание роли,
персональные настройки, блокировка и история изменения доступа. Карточка
показывает итоговые права и источник каждого: роль или личное правило.
Изменение роли обновляет всех её участников; личные исключения сохраняются.
Пользователь видит изменения перед подтверждением сохранения.

Входящий пользователь не получает доступ автоматически. Администратор заранее
добавляет Telegram ID и выбирает роль; человек входит под этим же проверенным
ID. В первой версии не нужны свободная регистрация и приглашения по email.

## 3D и движение

Настоящая сцена Three.js; изображение не вращается плоским слоем. Геометрия
собирается процедурно: независимые металлические кольца, световые вставки,
внутренняя сфера, оболочка и частицы. Нет API генерации, облачного рендера,
внешних моделей, трекеров или платных запросов для анимации.

Кольца движутся вокруг разных осей с различными скоростями и фазами.
Скорость зависит от времени, а не частоты кадров. Корпус медленно покачивается;
свет меняется мягко, без вспышек. Касание/перетаскивание даёт инерционный
поворот. Есть пауза и регулировка интенсивности. Вертикальный скролл сохраняется.

Цель: 60 fps на обычном современном устройстве, сниженное качество на слабом.
Это бюджет, а не подтверждённый результат на телефоне. DPR ограничен, сцена
приостанавливается вне viewport и в скрытой вкладке. Reduced motion означает
неподвижную сцену, пока человек сам не включит движение. При отказе WebGL
показывается статичный вариант, интерфейс остаётся доступным. Контекст GPU,
геометрии, материалы и обработчики освобождаются при размонтировании.

## Сервер и безопасность

Существующий Fastify/CommonJS и PostgreSQL остаются источником истины.
Новый клиент не должен изменять владельца ресурса на основе тела запроса.
Telegram initData проверяется сервером: HMAC, auth_date, срок, закрытая
форма и ограничения размера. initDataUnsafe не является доказательством
идентичности. Проверенные данные обмениваются на короткую отзываемую сессию;
сессионные секреты и исходный initData не попадают в URL, localStorage или логи.
Изменения имеют CSRF/origin-защиту, ограничение частоты и подтверждение.
Telegram Web требует отдельного frame/CSP-контракта только для /mini/;
глобальная защита остальных страниц не ослабляется.

Предлагаемые маленькие модули: access/permissionCatalog.js,
access/accessPolicy.js, access/accessRepository.js, access/accessService.js;
miniApp/initData.js, miniApp/sessionService.js, miniApp/routes.js.
Новые таблицы вводятся forward-only migration после текущей 036.
Имена таблиц: access_roles, access_role_permissions, access_memberships,
access_user_overrides, access_audit, mini_app_sessions.
Роли и overrides изменяются транзакционно с revision/CAS. Аудит хранит
действующего администратора, объект, фиксированные права до/после и время;
без текстов диалогов и credentials. Повтор подтверждённого изменения
проверяется по исходному operation ID.

Владелец фиксируется существующей серверной конфигурацией, а не полем из
браузера. Только владелец изменяет административный статус. Другой администратор
не может повысить себя, изменить владельца или выдать права доступа к чужим
данным. Галочки обычной роли не включают административные привилегии.

Меню, callbacks, сообщения/voice/files, guided input, API, фоновые задания
и непосредственное выполнение действий используют одну проверку доступа.
Проверка повторяется перед действием и потреблением подтверждения. Отзыв права
останавливает новые запуски и выдачу данных; уже отправленная операция
с неопределённым результатом сверяется по её исходному ID.

Поиск работы требует отдельных пользовательских подключений HH. Существующие
owner-only проверки в jobTelegramService и jobSearchRepository заменяются
проверкой права jobs, с сохранением private-chat и user scope. Нельзя просто
пометить всех участников owner. Общие лимиты ресурсов и очередь должны
учитывать нескольких пользователей. Старый Operations browser login и
Supervisor сохраняют текущие границы до отдельной реализации делегирования.
Галочка operations не должна обещать пользователю несуществующий доступ.

## Этапы и критерии готовности

1. Живой локальный образец 3D и экранов на вымышленных Telegram ID. Явная
   маркировка демонстрации; никаких реальных административных запросов.
2. После проверки письменной спецификации — подробный план, миграция и
   серверные проверки ролей, затем проверяемый вход Telegram и Mini App API.
3. Подключение админки к настоящему API и серверному аудиту; перенос проверок
   во все затронутые пути, затем собственный поиск работы для второго человека.
4. Функциональные тесты owner/admin/member/blocked, поддельного и старого
   initData, чужого ресурса, CAS, повторов и отзыва прав во время задания.
   Настоящие PostgreSQL handlers проверяются отдельно от mocks.
5. Browser QA 320/390/desktop, keyboard, reduced motion, WebGL fallback,
   прекращение рендера в фоне; полный server/npm test перед выпуском.
6. По отдельному поручению владельца публикация, обновление обоих VPS,
   HTTPS и настройка запуска в Telegram; живая проверка двумя аккаунтами.

Ни локальный образец, ни fixtures не подтверждают реальную авторизацию,
применённую migration, установленный сервер или доступ к HH второго человека.
Windows Desktop не требует пересборки, пока его runtime/ресурсы не затронуты.
