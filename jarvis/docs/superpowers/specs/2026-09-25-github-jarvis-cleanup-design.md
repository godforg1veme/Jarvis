# План наведения порядка в репозитории Jarvis

**Дата:** 2026-09-25
**Статус:** проект согласован; реализация начнётся после проверки этого документа владельцем.

## Цель

Сделать один очевидный и проверяемый источник проекта: публичный репозиторий
`godforg1veme/Jarvis`, ветка `main`, файлы проекта в корне репозитория и
рабочая папка Windows `F:\test\jarvis`. Сохранить полезные изменения из GitHub,
локальных веток и рабочих копий, убрать подтверждённые дубли, а затем привести
документацию и нужные установки к этому состоянию.

Отдельная цель — исправить создание и переименование профиля VPN-подписки Happ.
Оба действия должны проходить от Telegram callback до сохранённого результата,
с проверками доступа и контекста. Они не должны менять уже выданные клиентские
данные или токен подписки при простом переименовании.

## Что будет сделано

### 1. Инвентаризация и сохранность

- Перед изменениями повторно получить состояние GitHub и локальных Git-ссылок,
  веток, worktree и stash.
- Для каждой удалённой и локальной ветки установить назначение и сравнить её
  коммиты с `main`. Перенести на `main` только полезные изменения, которых там
  действительно нет; эквивалентные и устаревшие изменения не дублировать.
- Не удалять ветку, stash, каталог, резервную копию или серверный файл, пока
  его содержимое не классифицировано и нужные изменения не проверены в `main`.
- Сохранить `.env`, `data/`, модели, голоса, пользовательское состояние,
  резервные копии, секреты и незавершённые идентификаторы операций. Не включать
  их в Git, архив релиза, логи или отчёт.

### 2. Единый корень и инструкции

- Перенести отслеживаемое содержимое нынешней `jarvis/` в корень репозитория.
- Сделать `F:\test\jarvis` единственной чистой локальной Git-рабочей папкой.
  Перестройку выполнить через отдельную проверенную копию; локальное состояние
  переносить отдельно от исходников, учитывая `.gitignore`.
- Перенести главные `README.md` и `AGENTS.md` в корень. Удалить вводящие в
  заблуждение обёртки и ссылки на вложенную папку, обновить тесты и скрипты,
  которые проверяют старые пути. Сохранить исторические спецификации и планы,
  помечая устаревший статус вместо переписывания истории.
- Зафиксировать в `AGENTS.md` правило для Telegram guided input: каждый новый
  interaction kind должен одновременно поддерживаться валидатором приложения,
  валидатором контекста и ограничением базы данных. Контрактный тест должен
  обнаруживать рассинхронизацию этих трёх частей.
- Переписать верхний README и GitHub About понятным, человеческим языком, на
  основе проверенных функций проекта. Проверить индекс `docs/README.md` и
  остальные README, исправляя только устаревшие сведения и пути.

### 3. Создание и переименование Happ-профиля

- Проследить оба Telegram-сценария по цепочке: callback, начало диалога,
  проверка interaction kind и контекста, запись результата, ответ пользователю.
- Согласовать разрешённые типы ввода и поля контекста в приложении с
  PostgreSQL `CHECK` constraint. Добавить необходимую миграцию без ослабления
  проверки владельца, диалога и исходного чата.
- Проверить новый профиль: имя принимается, профиль и привязка создаются ровно
  один раз, а пользователь получает корректный ответ. Проверить неверный и
  повторный ввод.
- Проверить переименование: сохраняются идентификатор, токен, привязанные
  клиенты и доступ; меняется только отображаемое имя. Проверить пустое и
  недопустимое имя, неверный контекст и чужой профиль.
- Добавить автоматические регрессионные проверки на валидатор,
  миграционный контракт и оба сквозных Telegram-сценария. Сквозной прогон
  использовать с изолированной тестовой БД/фикстурами; не создавать и не
  переименовывать реальные пользовательские профили.
- Не менять Telegram-меню, подписи кнопок, порядок, callback-грамматику или
  правила видимости без отдельной необходимости и соответствующего изменения
  контракта меню.

### 4. GitHub и единая ветка

- Переименовать существующий GitHub-репозиторий в `Jarvis`, сохраняя его
  историю и содержимое; обновить `origin` в локальной рабочей копии и на
  известных VPS.
- Свести проверенные изменения в `main`, отправить итог и после повторной
  проверки удалить только те удалённые и локальные тематические ветки, чьи
  полезные коммиты уже находятся в `main` или доказанно дублируют её.
- Оставить `main` единственной постоянной веткой. Перед удалением сверить
  актуальные refs, открытые PR и ancestry; не применять force-push.
- Обновить краткое описание репозитория и подходящие GitHub topics. Текст
  README должен сообщать назначение проекта, подтверждённые компоненты,
  быстрый старт и ссылки на документацию и правила безопасности.

### 5. Проверка и развёртывание

- Сначала прогнать точечные проверки VPN-ввода и миграции, затем полный набор
  серверных и относящихся к затронутым компонентам тестов. Выполнить проверки
  форматирования/сборки, если они предусмотрены текущим проектом.
- Собрать и установить актуальный Windows Desktop, если после сверки версия на
  этом ПК устарела. Подтвердить установленную версию и запуск; не удалять
  прежний установщик до проверки нового.
- Для production сначала проверить Git-состояние, compose health, миграции,
  резервное копирование и текущие флаги VPN Supervisor с записью owner
  acceptance. Разворачивать только проверенный код, сохраняя `.env`, тома,
  резервные копии и маркеры незавершённых операций. После развёртывания
  проверить readiness, миграцию, основные API/Telegram-диагностики и актуальный
  rollout record.
- Второй VPS менять только если инвентаризация покажет, что новый код там
  нужен. Если изменение касается только Host Agent, обновлять только его по
  штатному безопасному порядку; не устанавливать Docker или полный Compose
  стек без необходимости.
- Не выполнять VPN-перезапуски, выпуск/отзыв ключей, ротацию токенов или иные
  реальные изменяющие операции в рамках проверки.

## Критерии завершения

1. GitHub открывает проект с корневым Jarvis README и исходниками, без
   промежуточной папки `jarvis/`.
2. Итоговый `main` содержит все отобранные полезные изменения, а состояние
   каждой ветки из исходного списка объяснено в отчёте. Удалены только
   проверенные устаревшие/слитые ветки.
3. `F:\test\jarvis` — чистая рабочая копия итогового `main`; `.env`, данные,
   модели, пользовательские файлы и резервные копии сохранены вне Git.
4. Создание и переименование проверены сквозными автоматическими тестами.
   Переименование не меняет токен или привязанные клиентские данные.
5. Релевантные серверные тесты и сборки завершены; все ошибки, пропуски и
   непроверенные пункты перечислены явно, без утверждений о непроведённых
   проверках.
6. Если обновлялись Desktop или VPS, подтверждены фактическая установленная
   версия и состояние сервиса после обновления. Секреты и персональные данные
   не попали в Git или отчёт.
7. README, описание репозитория и инструкции агентов совпадают с реально
   проверенным состоянием.

## Границы

- Работа не включает общий редизайн Telegram-кнопок или смену VPN-архитектуры.
- Нельзя удалять пользовательские данные, действующие резервные копии,
  секреты, volumes или неопределённые маркеры операции ради косметической
  чистоты Git.
- Исторические документы не переписываются задним числом.
- Любой дефект, обнаруженный вне согласованного объёма, документируется
  отдельно и не исправляется без необходимости для безопасной консолидации.

## Риски и способ контроля

Переименование GitHub и перенос корня затрагивают clone URL и пути сборки.
Поэтому сначала сохраняется проверенная исходная точка и готовится новая
структура, затем проверяются команды и ссылки до публикации. Удаление refs
выполняется после проверки ancestry и CI. Развёртывание выполняется только
после прохождения тестов и проверки миграции, с сохранением локальных данных и
проверяемым способом отката. При любом расхождении фактического состояния с
этим планом сначала сохраняется состояние и обновляется инвентаризация, затем
принимается следующее решение.
