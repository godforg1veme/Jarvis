# Jarvis Family Cloud Assistant Design

Status: approved by the user on 2026-09-01.

## Goal

Turn the existing Windows Jarvis application into an always-available family
assistant whose server-side identity, memory, knowledge base, voice input, and
agent orchestration continue working while the owner's PC is off.

The first client is a Telegram bot. A PWA will later use the same server API.
Each person has an isolated account and private long-term memory. A person may
connect several devices to the same account and ask the server-side assistant
to operate a selected Windows PC through the existing safe Node Tool Gateway.

## Selected Deployment

The always-on control plane runs on one DE-4 VPS:

- Ubuntu Server 22.04 LTS;
- 6 vCPU AMD Ryzen 9 5950X;
- 16 GB RAM;
- 200 GB NVMe;
- 1 Gbit/s network;
- Docker Compose for application services;
- Caddy for HTTPS and secure WebSockets;
- PostgreSQL with pgvector as the source of truth.

Ubuntu 22.04 is an explicit initial constraint. Its standard support ends in
2027, so an upgrade rehearsal and migration to a newer LTS must be completed
before standard support ends. Application runtimes are containerized to reduce
host-OS coupling.

The DE-4 does not run the main LLM. It uses a model gateway that can call:

1. a self-hosted Gemma 4 12B Q4 endpoint on Salad;
2. OpenRouter as a manually selected provider or automatic fallback.

Qwen3-ASR 1.7B Q4 is evaluated as the primary always-on server ASR. The ASR
interface remains replaceable because CPU latency and Russian command accuracy
must be measured on the real DE-4. Faster Whisper remains a supported fallback.

## Scope

The first production slice includes:

- Telegram text and voice messages;
- a Telegram-ID allowlist and one internal user per person;
- private conversations, memories, documents, and knowledge-base retrieval;
- server-side ASR that works while the owner's PC is off;
- text answers and optional Silero/Piper voice answers;
- Salad and OpenRouter model providers behind one gateway;
- a server-side agent loop using explicit tool schemas;
- multiple devices per user and one default device per device type;
- remote operation of an online Windows Jarvis Device Agent;
- two action categories: safe and changing;
- confirmation of every changing action in the channel that originated it;
- a separate personal WireGuard VPN for 10-20 personal phones/devices;
- encrypted off-server database and document backups;
- audit records for agent actions without raw audio or secrets.

Out of scope for the first production slice:

- PWA implementation;
- continuous camera streaming;
- native mobile applications;
- fine-tuning model weights from conversations;
- unrestricted shell or PowerShell generated by an LLM;
- public self-registration;
- shared family knowledge spaces;
- high-concurrency ASR or LLM serving.

## Architecture

```text
Telegram
  -> Jarvis Server on DE-4
       -> identity and access
       -> conversation and memory service
       -> knowledge retrieval
       -> Qwen3-ASR / fallback ASR
       -> agent orchestrator
       -> model gateway
            -> Salad / Gemma 4 12B Q4
            -> OpenRouter
       -> command dispatcher
            -> secure outbound WSS session from Windows Device Agent
                 -> existing Node Tool Gateway
       -> PostgreSQL + pgvector
       -> object/document storage

Personal phones
  -> separate WireGuard full/split tunnel on DE-4
  -> internet
```

The server is a modular monolith. Modules have explicit interfaces but are
deployed as one application initially:

```text
server/
  telegram/
  auth/
  users/
  devices/
  conversations/
  memory/
  knowledge/
  voice/
  models/
  agents/
  commands/
  confirmations/
  audit/
```

The actual path and language split will be chosen in the implementation plan
after mapping these boundaries onto the existing CommonJS Node application and
Python agent runtime. This design does not require a premature project-wide
migration.

## Identity and Device Model

The internal `user_id` is the root identity. External identities and devices
attach to it:

```text
user
  -> Telegram identity
  -> future PWA identity
  -> desktop PC
  -> laptop
  -> future phone client
  -> private conversations, memories, and documents
```

Core records include:

- `users`;
- `user_identities`;
- `devices`;
- `device_capabilities`;
- `device_sessions`;
- `conversations` and `messages`;
- `memories` and `memory_versions`;
- `documents` and `document_chunks`;
- `commands` and `command_steps`;
- `confirmations`;
- `audit_events`.

Every user-owned row carries a `user_id`. Retrieval always applies the user
scope before semantic or keyword ranking. One device can be marked as the
default PC. Explicit device names override the default. If selection remains
ambiguous, the assistant asks instead of guessing.

## Device Enrollment and Connectivity

Jarvis device control does not require a service VPN. A Windows Device Agent
opens an outbound WSS connection to DE-4, which works through NAT without
opening an inbound PC port.

Enrollment is intentionally simple:

1. an allowed user asks the Telegram bot to add a device;
2. the server creates a short-lived one-time pairing code;
3. the code is entered into the Device Agent;
4. the server issues a long random device token;
5. the token is mapped to `user_id` and `device_id`;
6. the user can revoke that device later.

Baseline protection consists of HTTPS/WSS, Telegram allowlisting, pairing,
per-device tokens, user/device ownership checks, action policy, and changing-
action confirmation. There is no service WireGuard, mTLS, or per-command
public-key signature in the MVP.

## Agent and Tool Execution

Gemma understands requests, reasons, chooses tools, and explains results. It
never receives unrestricted access to a shell or the filesystem.

The server-side Agent Orchestrator runs a bounded loop:

```text
request
  -> retrieve user context
  -> model proposes a structured tool call
  -> validate schema, ownership, capabilities, and policy
  -> dispatch to the selected online device
  -> existing Node Tool Gateway executes the concrete operation
  -> return observation to the model
  -> continue or produce the final answer
```

The initial limit is eight model/tool steps per request. A malformed or
unsupported call is rejected. An ambiguous request produces a question. A
failed tool result is returned to the model for at most one corrected attempt
unless the failure is non-retryable.

Existing deterministic intent parsing stays ahead of the agent for cheap,
unambiguous commands. Complex, multi-step, knowledge-dependent, or ambiguous
requests use the agent.

Tools are narrow operations such as file search, file read, application open,
system information, window observation, and explicitly implemented mutations.
The Node Tool Gateway remains the execution authority.

## Action Policy and Confirmation

There are two user-visible policy categories:

- `safe`: read-only or non-mutating operations such as search, inspect, list,
  retrieve status, or open an already trusted application;
- `changing`: every state-changing operation, including actions that would
  otherwise be described as dangerous.

Safe actions may execute automatically. Changing actions always require an
explicit confirmation in the originating channel:

- Telegram request -> Telegram inline confirmation;
- future PWA request -> PWA confirmation;
- local desktop request -> desktop confirmation.

A confirmation binds to the user, originating channel/session, device, exact
normalized action, and expiration time. The default expiration is two minutes.
Changing commands do not execute after expiration or with altered arguments.

## Model Gateway

The Agent Orchestrator uses one internal model contract rather than provider-
specific calls. Provider adapters normalize messages, multimodal inputs, tool
schemas, thinking settings, timeouts, errors, and usage metadata.

Supported operating modes:

- `salad`: use the self-hosted Gemma endpoint only;
- `openrouter`: use the configured OpenRouter model only;
- `auto`: prefer Salad and fall back to OpenRouter when policy permits;
- `manual`: owner selects the active provider in settings.

Provider capability metadata includes text, vision, thinking, tool calling,
maximum context, and health. Unsupported requests fail clearly or route to a
capable configured fallback; they are not silently degraded.

Conversation history and memory live in PostgreSQL, not in provider-managed
threads. Switching providers therefore preserves the conversation. API keys
remain in server secrets/environment configuration and never enter the repo,
database content, Telegram messages, or audit log.

## Voice Pipeline

Telegram voice messages follow this path:

```text
Telegram audio
  -> bounded temporary file or stream
  -> normalize to supported mono audio
  -> ASR queue
  -> Qwen3-ASR 1.7B Q4 or configured fallback
  -> transcript
  -> deterministic router or Agent Orchestrator
  -> text response
  -> optional Silero/Piper audio response
```

The server processes complete short utterances instead of relying on long-lived
Qwen streaming. Default audio retention is delete-after-transcription. The
transcript is stored as part of the conversation; raw audio is stored only if a
future explicit per-user retention setting is introduced.

ASR runs with one active transcription initially and queues additional jobs.
Text messages bypass that queue. Acceptance benchmarks compare Qwen3-ASR 1.7B
Q4 with the existing Faster Whisper behavior on Russian commands, names,
background noise, latency, CPU, and memory. The interface must allow replacing
the model without changing Telegram or conversation code.

## Memory and Knowledge

The assistant does not fine-tune its weights after each conversation. It uses
four memory layers:

1. recent messages passed verbatim within a bounded active window;
2. structured episodic summaries of long or completed conversations;
3. durable facts, preferences, decisions, and device information;
4. a searchable full message archive.

Documents form a fifth retrieval source. They are parsed, chunked, embedded,
and indexed for hybrid keyword and vector retrieval. Retrieved answers cite
their document or conversation source.

Durable memories store owner, source reference, creation time, confidence,
validity state, and version lineage. New information can supersede an old fact
without deleting its historical meaning. The user can ask the assistant to
remember, forget, correct, or list remembered facts.

Normal speculation is not promoted automatically. Stable explicit facts,
confirmed decisions, repeated preferences, and verified tool outcomes may be
promoted. Passwords, API keys, banking data, and authentication secrets are
never automatically stored as long-term memories.

## Personal WireGuard VPN

The DE-4 also hosts a separate personal WireGuard VPN for approximately 10-20
phones or personal devices. It is operationally independent of Jarvis device
control.

Each VPN device receives an individual key so it can be revoked independently.
Firewall rules prevent the VPN from directly reaching PostgreSQL and internal
container management ports. Split tunnel is preferred when only selected
traffic needs the VPS. Full tunnel is allowed subject to the provider's traffic
policy.

Heavy VPN traffic must not starve voice processing. The deployment plan must
include network rate limits or service prioritization and measure ASR latency
while VPN traffic is active.

## Failure Handling

- If Salad is unavailable, `auto` mode may use OpenRouter; fixed `salad` mode
  reports the outage without losing the request or history.
- If all LLMs are unavailable, Telegram, memory storage, VPN, deterministic
  commands, and device presence continue to work.
- If ASR is unavailable, text remains available and voice returns a clear
  retry/text instruction.
- If a target PC is offline, the assistant reports it. Safe queued work may be
  offered, but a changing action requires fresh confirmation after reconnect.
- If the Device Agent disconnects mid-command, no changing step is replayed
  automatically.
- If a tool call fails, execution stops or performs the one bounded correction
  allowed by the agent policy.
- Expired confirmations are cancelled and cannot be reused.
- PostgreSQL-backed state restores conversations, memories, device ownership,
  and non-mutating queues after a server restart.

## Data Protection and Operations

- PostgreSQL is not publicly exposed.
- Caddy terminates public HTTPS/WSS.
- Secrets use environment/secret files with restricted permissions.
- Daily encrypted PostgreSQL backups and document backups are copied off the
  DE-4.
- Several daily and weekly restore points are retained.
- Restore is tested on a clean environment before the MVP is declared ready.
- Audit events include actor, device, normalized tool/action, confirmation,
  timestamps, and result, but exclude raw audio, API keys, and unnecessary
  document contents.
- Logs use bounded retention and redact tokens and Telegram secrets.

## Delivery Sequence

1. Provision Ubuntu 22.04, patch it, configure SSH, Docker Compose, Caddy,
   firewall, PostgreSQL/pgvector, backups, and the independent WireGuard VPN.
2. Build the Telegram adapter, allowlist, internal users, conversations, and a
   minimal OpenRouter-backed Model Gateway.
3. Add layered memory, document ingestion, embeddings, hybrid retrieval, and
   source citations.
4. Deploy and benchmark server ASR; select Qwen3-ASR 1.7B Q4 or the measured
   fallback without changing the voice interface.
5. Deploy Gemma 4 12B Q4 on Salad and implement provider selection, health,
   timeout, and fallback behavior.
6. Add device enrollment and outbound WSS sessions, reusing the existing Node
   Tool Gateway for initial safe tools.
7. Add the bounded Agent Orchestrator and introduce changing tools one at a
   time with originating-channel confirmation.
8. Verify isolation, recovery, provider switching, VPN coexistence, backups,
   and family acceptance scenarios.
9. After the MVP is stable, design the PWA and camera phases against the same
   APIs.

## Verification

Automated verification must cover:

- Telegram allowlist and identity mapping;
- user-scoped queries and attempts to cross user boundaries;
- multiple devices, default-device selection, ambiguity, and offline status;
- pairing-code expiration, device-token revocation, and WSS reconnect;
- safe versus changing policy classification;
- exact-action confirmation binding and expiration;
- model-provider manual selection, capability checks, timeouts, and fallback;
- conversation continuity when switching Salad/OpenRouter;
- memory extraction, versioning, correction, forgetting, and retrieval;
- document access isolation and source citations;
- ASR queue behavior, temporary-audio deletion, and fallback;
- agent step limit, schema rejection, tool failure, and no automatic mutation
  replay;
- database backup and clean restore;
- VPN firewall isolation and ASR latency under VPN traffic.

The existing Jarvis test suites remain required for touched local voice,
intent, agent, and Tool Gateway behavior.

## Acceptance Criteria

The MVP is ready when all of the following are demonstrated:

1. Two allowed family users share one Telegram bot but cannot retrieve each
   other's messages, memories, documents, or devices.
2. A user sends a voice message while the owner's PC is off and receives a
   server-transcribed answer.
3. A user uploads a private document and receives a sourced answer about it.
4. A user asks the bot to perform a safe operation on the user's online default
   PC and receives the real tool result.
5. A changing operation executes only after confirmation in the originating
   Telegram conversation and cannot be replayed.
6. An offline or ambiguous target device produces an explanation or question,
   not a guessed execution.
7. The owner switches between Salad and OpenRouter without losing conversation
   history or personal memory.
8. A DE-4 restart preserves identities, memory, documents, device ownership,
   and valid recoverable work without replaying mutations.
9. The independent WireGuard VPN serves personal devices without exposing
   PostgreSQL or making ASR unusable.
10. Encrypted off-server backups restore successfully into a clean deployment.
