# Оформление Jarvis как публичного проекта

Дата: 2026-08-24
Статус: дизайн утверждён

## Цель

Оформить репозиторий Jarvis так, чтобы новый читатель без знакомства с кодом
быстро понял:

- какую пользовательскую задачу решает проект;
- что уже реализовано и проверено;
- как система работает на техническом уровне;
- где проходят границы безопасности и ответственности AI;
- какие ограничения остаются честно открытыми;
- какие инженерные решения демонстрирует проект потенциальному клиенту.

Документация должна быть полностью на русском языке и подходить одновременно
для первого знакомства, технической оценки и обсуждения проекта с клиентом.

## Выбранный формат

Документация делится на два уровня:

1. `README.md` — компактная витрина проекта и основная входная точка GitHub.
2. `docs/PROJECT_OVERVIEW.md` — подробное человеческое и техническое описание.

Такое разделение сохраняет README удобным для быстрого просмотра и не скрывает
важные детали реализации за рекламными формулировками.

## Структура README

README содержит:

1. Название и короткое позиционирование Jarvis как персонального Windows-
   ассистента с локальным голосовым интерфейсом и контролируемым Desktop Agent.
2. Раздел «Зачем этот проект» с человеческим объяснением пользы.
3. Реальные сценарии использования без обещаний несуществующих функций.
4. Краткую сводку реализованных возможностей:
   - консоль запуска и история;
   - локальное распознавание речи;
   - TTS;
   - запуск приложений;
   - безопасные файловые команды;
   - Desktop Agent для многошаговых задач;
   - управление окнами;
   - подтверждения и журнал выполнения.
5. Mermaid-схему основных компонентов и потока команды.
6. Объяснение трёх уровней принятия решений:
   - детерминированные локальные правила;
   - необязательный OpenRouter для простого fallback;
   - Python/Gemini Desktop Agent для планирования сложных задач.
7. Краткое описание модели безопасности и роли Node Tool Gateway.
8. Технологический стек и структуру репозитория.
9. Инструкции по установке, запуску и основным проверкам.
10. Ссылку на полный обзор проекта.
11. Честные ограничения и следующий запланированный этап.

README не должен включать фиктивные метрики, отзывы, клиентские результаты,
неподтверждённую кроссплатформенность или обещание полностью автономного
управления компьютером.

## Структура полного обзора

`docs/PROJECT_OVERVIEW.md` содержит:

1. Человеческое описание проблемы и выбранного подхода.
2. Пользовательский путь для текстовой, голосовой и агентной команды.
3. Подробную архитектуру Electron/Node/Python с границами модулей.
4. Описание локального intent routing и необязательных AI-провайдеров.
5. Жизненный цикл Desktop Agent:
   наблюдение, план, выбор пользователя, подтверждение, выполнение, отчёт.
6. Описание файловых, оконных, голосовых и TTS-подсистем.
7. Модель безопасности:
   валидация схем, allowlist, уровни риска, ordinary/strong confirmation,
   лимит batch-операций и отсутствие прямых tool calls из LLM.
8. Локальное состояние и правила работы с секретами.
9. Итоги завершённого этапа разработки.
10. Проверки и доказательства текущего состояния.
11. Технически честные ограничения и дальнейшее направление Browser Agent.
12. Краткое объяснение того, какие компетенции демонстрирует проект.

## Источники истины

Формулировки сверяются с текущим кодом и следующими документами:

- `AGENTS.md`;
- `README.md`;
- `docs/superpowers/specs/2026-06-18-jarvis-desktop-agent-design.md`;
- `docs/superpowers/specs/2026-06-18-jarvis-file-commands-design.md`;
- `docs/superpowers/specs/2026-08-23-jarvis-unified-intent-routing-design.md`;
- соответствующими implementation plans;
- текущими модулями `main.js`, `agents/`, `agent_runtime/`, `voice/`, `tts/`,
  `tools/` и `renderer/`.

Если ранний план и текущий код расходятся, документация описывает фактическое
поведение кода и отдельно отмечает внешнее или ещё не реализованное ограничение.

## Тон и оформление

- Основной язык — русский.
- Стиль — профессиональный, ясный и предметный.
- Человеческое объяснение предшествует деталям реализации.
- Термины расшифровываются при первом использовании.
- Возможности описываются через проверяемое поведение.
- Технические ограничения не маскируются маркетинговыми формулировками.
- Структура оптимизирована под просмотр на GitHub без отдельного сайта.

## Проверка качества

Перед публикацией необходимо:

1. Проверить все локальные ссылки и пути.
2. Убедиться, что Mermaid использует поддерживаемый GitHub синтаксис.
3. Сверить команды установки и тестирования с `package.json`, `AGENTS.md` и
   реальными скриптами.
4. Проверить отсутствие секретов, локальных путей пользователя и generated
   state в документации и коммите.
5. Выполнить поиск `TODO`, `TBD`, пустых разделов и незакрытых чекбоксов.
6. Выполнить `git diff --check`.
7. Убедиться, что итоговый коммит содержит только ожидаемую документацию.
8. После push проверить чистое рабочее дерево и нулевой ahead/behind относительно
   `origin/main`.

## Результат

После реализации репозиторий должен отвечать на два вопроса без необходимости
сразу читать код:

1. «Что Jarvis делает для пользователя и почему это полезно?»
2. «Как Jarvis устроен, какие меры безопасности применяет и что именно уже
   проверено?»
