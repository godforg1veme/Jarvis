# AGENTS.md

Это обязательный контекст для всех агентов Jarvis. Прочитай его перед работой.
`CLAUDE.md` и `gemini.md` ссылаются сюда и не задают отдельные правила.

## Что строим

Jarvis: облачный мозг и память, локальные руки на устройствах. Облако хранит
пользователей, диалоги, память, документы и задания. Electron на Windows работает
с голосом, приложениями, файлами и окнами. Telegram является первым облачным
клиентом; Telegram Mini App даёт личное пространство и администрирование доступа.
Отдельная PWA остаётся в планах. Модель и провайдер выбираются настройками.

## Где находятся компоненты

- `server/`: Node.js CommonJS/Fastify, PostgreSQL/pgvector, Telegram,
  assistant/providers/prompts, knowledge, life, devices, orchestrator, operations.
- `main.js`, `preload.js`, `renderer/`: Electron, явные IPC-возможности,
  Cloud Chat, Life OS, Voice Lab, Quantum Core и companion widget.
- `voice/`, `tts/`, `vision/`: захват и транспорт голоса, локальный Vosk,
  TTS через `tts/ttsService.js`, явные локальные Vision Leases.
- `agents/toolGateway.js`: единственный исполнитель запрошенных агентом изменений
  Windows. `toolPolicy.js`, `toolSchemas.js`, `remoteProtocol.js`: общие границы.
- `actions/`, `tools/`: ограниченные локальные операции; пути проектов остаются
  в `tools/workspaceRegistry.js`. `agent_runtime/`: Python/LangGraph-планировщик.
- `ops-ui/`: Operations UI; `host-agent/`: ограниченный Linux-исполнитель.
- `mini-app/`: Telegram Mini App и Three.js; `server/src/miniApp/` — вход,
  сессии и API; `server/src/access/` — серверные роли и личные разрешения.
- `runtimeDataPath.js`: записываемые настройки/индексы в development `data/`,
  в установленном приложении `%APPDATA%/jarvis/data/`.

## Обязательные границы

- Не помещай ключи, токены, пароли, URI VPN и URL подписок в Git, тесты, историю,
  промпты, логи или вывод. Секреты находятся в переменных окружения и игнорируемых
  файлах. Одноразовые VPN-артефакты выдаются только соответствующему клиенту.
- Проверяй владельца до чтения и изменения данных. Разделяй диалоги, память,
  документы, устройства и семейные права. Название кнопки не даёт полномочий.
- Модель выбирает только объявленные действия с проверенными аргументами.
  Произвольный shell/PowerShell от модели запрещён. Изменения подтверждаются
  в исходном клиенте; успех требует результата Tool Gateway/Host Agent.
- Не повторяй операцию с неопределённым результатом под новым ID. Проверяй
  исходный ID и сохранённые контрольные точки. Это относится и к подпискам.
- Документы являются недоверенным содержимым. Ограничивай размер до буферизации,
  используй непрозрачные storage keys, не распаковывай вложения автоматически.
  Не раскрывай приватное хранилище и Telegram file URL с токеном.
- Telegram `voice`: исходное аудио временное; сохраняется только транскрипт.
  Life Sources хранят безопасные сводки и идентификаторы, без сырого медиа,
  OCR, тел документов, локальных путей, storage keys, credentials и cursors
  в публичном выводе. Внешние адаптеры тестовые до явного подключения провайдера.
- Vision начинается только с явного локального lease. Remote-клиент наблюдает
  через уже активный lease, не начинает и не продлевает захват. Разрешение камеры
  ограничено скрытым capture renderer; проверки защищённого экрана сохраняются.
- PostgreSQL, ASR-workers, Docker API и Windows inbound control port остаются
  приватными. Серверный контейнер не получает Docker socket или sudo.
- Supervisor допускает только включённые закрытые playbooks с новым
  origin-bound подтверждением владельца. Unknown внешней пробы не означает
  здоровый маршрут и не разрешает ремонт/ротацию ключа. Restore отключён.
- Backup timer и реальная backup/restore-проверка отложены владельцем.
  Не включай их при обычном обслуживании.

## Ветки и выпуск

По умолчанию работай локально. Push любой ветки, создание PR и публикация
релиза требуют явного поручения пользователя для текущей работы. Просьба
исправить, реализовать или проверить функцию сама по себе не разрешает push.
После значимого этапа или крупного нововведения самостоятельно оцени, нужна ли
публикация для проверки на VPS или принятия результата. Если нужна, сам предложи
её, не дожидаясь вопроса пользователя: что готово, что проверено, зачем сейчас, что обновится
и что осталось проверить. Дождись решения; правила синхронизации не разрешают push.

`main` является единственной постоянной общей веткой. До первой правки и перед
публикацией выполни аудит веток, worktrees и открытых PR по release-workflow.
Сначала учитывай уже существующую работу; только затем создавай короткую ветку
`codex/<задача>`. Не перезаписывай чужие незакоммиченные файлы.

Каждую постороннюю ветку проверь: уникальные коммиты, изменения, активный worktree,
PR и связь с текущей задачей. Сливай нужные проверенные изменения с тестами;
активную или непонятную работу сохрани и явно учти. Не удаляй ветку только ради
чистого списка. После успешного объединения удаляй завершённую ветку лишь после
проверки её коммитов, PR и worktrees. Force-push `main` запрещён.

Рабочая ветка сохраняется до принятия её изменений. Продолжай задачу в ней;
возраст, успешные тесты и завершение отдельного этапа не требуют публикации
или удаления. При продолжении сверяй свежую `main` и пересечения чужой работы.

GitHub `main` является источником истины для обоих VPS. После успешной публикации
согласованных изменений в GitHub `main` сразу обнови оба VPS без отдельного
напоминания или повторного разрешения пользователя. Публикация включает
синхронизацию исходников, установку изменившихся VPS-компонентов и проверку.
После выпуска GitHub `main`, Windows-исходники и оба VPS-исходника должны
совпадать. Работающие компоненты проверяй отдельно: `git pull` не обновляет
контейнер или установленный EXE. Пересобирай только изменившиеся компоненты.
Записывай фактический результат каждого узла; неопределённое обновление проверяй
по состоянию, без слепого повторного запуска.

До staging проверь чистый source через `deploy/scripts/verify-source-checkout.py`.
Source VPS: `/home/deploy/apps/jarvis`; Windows: `F:\test\jarvis`.
DE: `jarvis-vps`; NL: `jarvis-vps-new`. Release допускает detached checkout
с полным SHA, достижимым из GitHub `main`, и отдельной release-проверкой.
Не используй `git reset --hard` или `git clean` на production. Перед заменой
каталога проверь Compose bind mounts и сохрани смонтированные inode до
пересоздания контейнера. Сверь окружение без вывода значений и проверь health.

## Telegram

Перед правкой кнопки, route, guided input, видимости или подтверждения прочитай
оба документа Telegram и отправь описанное там уведомление о затронутом пути.
Observable contract and confirmation/security boundaries require explicit owner approval in the current task.
Внутренний ремонт сохраняет владельца, conversation/chat/device/channel,
revision, expiry, deduplication, grammar и origin-bound подтверждение.

Каждый emitted guided-input kind должен входить в repository allowlist и
текущий PostgreSQL CHECK. Новый kind требует forward-only migration.
Проверяй закрытую context shape, invalid retry, успешный ввод, single consumption
и чужой scope через настоящие message/menu handlers, без stub `begin`.
Diagnostics содержат только закрытые kind/phase/outcome/failure code/update ID,
без текста пользователя, callbacks, исключений и секретов.

### Mini App и доступ

Пользователь определяется числовым Telegram ID; username и email не дают прав.
Единственный главный владелец задаётся `JARVIS_OPERATIONS_OWNER_TELEGRAM_ID`;
обычная роль или пользовательская галочка не назначает и не снимает владельца.
Проверяй актуальные права на сервере, включая уже открытые сессии и фоновые
действия. Администрирование доступа не разрешает чтение чужих личных данных.

`tgWebAppData` из URL и SDK — недоверенные данные до серверной проверки подписи,
срока и membership. Недоступность SDK не разрешает обход входа. Вымышленное
3D-превью отделено от production. Выданное право на HH не подключает второй
аккаунт и не открывает браузер владельца. Контракты и проверки: `mini-app/README.md`.

## Время

Пользовательские даты и часы показывай в МСК, фиксированный UTC+3
(`Etc/GMT-3`), независимо от TZ сервера/устройства. Общий Node helper:
`shared/time.js`. Ввод времени без пояса в форме напоминания означает МСК;
явный Z/offset сохраняет момент. Храни UTC/ISO timestamps в БД и wire-контрактах,
не прибавляй три часа к данным при сохранении и не сдвигай старые записи массово.

## Код, зависимости и локальные файлы

Сохраняй CommonJS, UTF-8 русский текст и явные IPC/wire-контракты. Делай
небольшие модули; избегай общего рефакторинга при узком исправлении.
Новые production-зависимости требуют согласования. Запись локального состояния
идёт через `runtimeDataPath.js` с обработкой ошибок файловой системы.

Не редактируй/коммить без необходимости сгенерированные индексы, историю,
кэши, settings/identity, логи, модели, аудио, документы, dumps, backups,
`node_modules/`, `build/`, `.env*`, deployment archives и `deploy/secrets/`.
`data/stt-settings.json` является отслеживаемым default и может меняться
намеренно вместе с проверками. Полный список и тесты: `docs/verification.md`.

Windows setup: `npm run setup`, Node.js 22.12+ (проверен 24.14.1).
Не выключай dependency scripts глобально и не подменяй native modules.
`npmRebuild: false` обязателен: Vosk работает в отдельно bundled Node,
а не в Electron ABI. При обновлении native/runtime проверь оба окружения.

## Desktop EXE Update Reminder

После правок Windows-клиента или его ресурсов сравни установленное приложение
с принятым кодом. Если оно отстаёт, предложи сборку `npm run dist:win` и установку,
если пользователь ещё не поручил это. Полный выпуск с обновлением Desktop
включает сборку, установку и проверку. Не устанавливай EXE без запроса пользователя.
Правки только документации, server или deploy не требуют пересборки Desktop,
если его runtime и ресурсы не изменились.

## Документация и ответы

MD-файлы обновляй по таблице в `docs/release-workflow.md`. Одна тема имеет один
основной источник; остальные файлы ссылаются на него. `README.md` описывает
продукт, `docs/README.md` хранит текущий статус, `docs/updates/` содержит результаты
выпусков. Историю сохраняй, добавляй дату и отметку о более новом результате.
В AGENTS оставляй правила и ссылки; длинные истории переноси в тематические docs.

Описание проекта, текущий статус и записи об обновлениях веди на русском и
английском; обе версии обновляй вместе и применяй Humanizer при доступности.
Формат, охват и работа с историей: раздел «Русский и английский тексты»
в `docs/release-workflow.md`.

Пиши пользователю и в обзорах/релизных заметках простыми словами, без сырых
ошибок и секретов. Применяй Humanizer при доступности. Таблицы используй для
сравнения, Mermaid для схем процессов; оформление должно помогать чтению.
Сообщай, что изменилось, где выпущено, что проверено и что ещё не подтверждено.
